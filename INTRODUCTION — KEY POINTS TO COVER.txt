Paragraph 1 — Global context (programming literacy):
  - Programming literacy is a 21st century requirement
  - HEIs worldwide expanding computing programs (NASEM, 2018)
  - PSU CCS is #1 HEI in Central Luzon (uniRank, 2025)
  - Introductory programming is the foundation of all CS education

Paragraph 2 — The persistent failure rate problem:
  - 25-40% failure rate globally in intro programming (Watson & Li, 2014)
  - Rate has not improved in a decade (Bennedsen & Caspersen, 2019)
  - Philippine context: identifying at-risk students is a concern
    (Bibangco & Dionson, 2024)
  - Recent confirmation the problem persists (Rahimi et al., 2025)

Paragraph 3 — Concept-level difficulty as root cause:
  - Students struggle specifically with loops, conditionals, OOP
    (Robins, 2019)
  - Undetected concept difficulties compound as course progresses
  - Difficulty identifying WHICH concept is the problem
    (Medeiros et al., 2019)
  - This is not a quality problem — it is a detection problem

Paragraph 4 — Existing systems and their gap:
  - Learning analytics can predict who is at risk
    (Hellas et al., 2018; Namoun & Alshanqiti, 2021)
  - LMS platforms track grades and assignments but not behavioral
    coding data (Rosa, 2023)
  - CodeChum does triage (tells instructor WHO to look at) but
    concept-level diagnosis remains manual (instructor reads code)
  - The gap: no system automatically diagnoses WHICH specific
    concept is causing difficulty AND identifies the underlying
    sub-concept (micro-concept) causing the confusion, while also
    ensuring that difficulty signals reflect genuine learning attempts

Paragraph 5 — What CodeInsight proposes:
  - Web-based concept difficulty analytics system
  - Transparent CDS (Concept Difficulty Score) formula grounded in three citations
  - Deterministic code structure verification using AST analysis + IBM Project CodeNet patterns
  - Rule-based micro-concept diagnosis (NOT AI/LLM) for specific sub-concepts
  - Academic integrity monitoring to ensure CDS accuracy reflects genuine learning
  - Instructor-facing analytics dashboard with heatmaps, alerts, and actionable reporting
  - Fills the gap: from triage to root-cause diagnosis to specific teaching intervention

─────────────────────────────────────────────────────────────────────────────
PURPOSE OF THE STUDY
─────────────────────────────────────────────────────────────────────────────

General objective:
  Design and develop CodeInsight — a web-based programming fundamentals
  concept difficulty analytics system to monitor and support beginner
  programmers in introductory programming courses at Pampanga State University.

Specific objectives — Updated to four (aligned with implementation):

  1. To design and develop a web-based system that enables instructors
     to create programming exercises manually tagged to specific
     programming concepts, and that accurately maps concept-level
     difficulty using a transparent, citation-grounded behavioral formula
     (CDS) protected by academic integrity safeguards that ensure difficulty
     scores reflect genuine learning attempts rather than shortcuts or cheating.

  2. To implement a difficulty analytics engine that captures behavioral
     coding data — error frequency, retry count, and time-on-task — to
     generate Concept Difficulty Scores (CDS) for each student per concept,
     enabling proactive identification of struggling students before poor
     grades manifest. CDS computation is protected by code structure
     verification to prevent hardcoding, memorization, and template-only
     submissions from artificially inflating success metrics.

  3. To develop an analytics dashboard presenting class-wide difficulty
     heatmaps, early warning alerts for high-difficulty students, individual
     student profiles, and rule-based micro-concept insights that translate
     raw behavioral data and code structural patterns into specific,
     actionable teaching recommendations without requiring AI/LLM services.

  4. To evaluate CodeInsight based on selected characteristics of
     ISO/IEC 25010:2011 — specifically Functional Suitability, Usability,
     and Performance Efficiency — using the System Usability Scale and
     pre- and post-assessment instruments.

─────────────────────────────────────────────────────────────────────────────
SIGNIFICANCE OF THE STUDY
─────────────────────────────────────────────────────────────────────────────

For instructors:
  Shifts from reactive grade-based monitoring to proactive concept-level
  early warning. Instructor knows not only WHICH concept is difficult but
  also the specific micro-concept mistake (e.g., "off-by-one error" within
  Loops, not just "Loops" in general), enabling targeted intervention without
  manual code reading. Academic integrity checks ensure alerts are based on
  genuine learning attempts, not student shortcuts.

For students:
  Transparent difficulty feedback combined with deterministic, rule-based
  guidance helps students understand their own conceptual gaps. When they
  submit code that violates a programming pattern, they immediately see
  specific, actionable feedback (not just "test failed"). Hidden test cases
  and structure verification ensure they cannot game the system through
  hardcoding or memorization.

For PSU CCS:
  Addresses persistently high failure rates in introductory programming
  by enabling earlier, more targeted conceptual intervention. Provides an
  open, institution-specific analytics tool independent of commercial
  platforms with proprietary methods. Zero per-submission costs (no LLM APIs).
  Maintains academic integrity by detecting and preventing learning shortcuts.

For the research community:
  Contributes a transparent, replicable, citation-grounded difficulty
  measurement formula to the body of learning analytics research in
  programming education. Demonstrates how deterministic rule-based
  micro-concept analysis achieves pedagogical value equivalent to
  AI-powered approaches without external API dependencies. Documents
  the integration of academic integrity safeguards into behavioral
  difficulty scoring, addressing the gap between data collection and
  concept-level diagnosis identified by Medeiros et al. (2019) and
  Paolucci et al. (2024).

SCOPE AND LIMITATION
─────────────────────────────────────────────────────────────────────────────

Scope:
  - PSU CCS, introductory C++ programming course, AY 2025-2026
  - Seven concepts: Datatypes, Variables, Conditionals, Loops,
    Functions, Arrays, OOP
  - Exercises created and tagged by instructor within CodeInsight
  - Behavioral data collected exclusively from in-platform activity
  - Code execution via direct GCC C++ compiler on local/cloud server
  - Code structure verification using tree-sitter AST + IBM Project CodeNet
    pattern matching (deterministic, not machine learning)
  - Micro-concept difficulty detection via rule-based analysis of:
    • Compiler error patterns (GCC)
    • Code structure (AST nodes present/absent)
    • Test case failure patterns (boundary cases, specific inputs)
  - Academic integrity monitoring via:
    • Hardcoding detection (literals in output instead of variables)
    • Blank/template-only submission detection (code unchanged from starter)
    • Behavioral anomaly detection (unusual patterns: instant success, extreme speed)
  - Deployed on Oracle Cloud free tier (or equivalent) for evaluation
  - Evaluated using ISO/IEC 25010:2011 (Functional Suitability,
    Usability, Performance Efficiency)

Limitations:
  - CDS reliability depends on instructor accuracy in concept tagging
  - CDS measures behavioral coding signals (not cognitive/affective factors)
  - Structure checker based on AST patterns — cannot catch all semantic
    workarounds (acknowledged in methodology)
  - Micro-concept rule coverage is bounded (not exhaustive for all possible
    mistakes, but covers 14+ common patterns across 7 concepts)
  - Hardcoding detection focuses on common patterns; sophisticated obfuscation
    may evade detection but is unlikely in introductory programming context
  - Code similarity detection between students is outside scope
    (future research direction; focus is micro-concept, not plagiarism detection)
  - Longitudinal effectiveness on pass rates not measured in this study
    (single-semester evaluation is insufficient for causal claims)
  - Peer-relative CDS requires minimum class participation for reliable
    normalization (flagged when fewer than 3 submissions)
  - System does not function as a full LMS — no grade computation,
    content delivery, or communication features
  - Student feedback on submissions is read-only (no multi-modal input)

THEORETICAL / CONCEPTUAL FRAMEWORK
─────────────────────────────────────────────────────────────────────────────

Four theoretical pillars ground CodeInsight:

PILLAR 1 — Behavioral Learning Analytics
  Source: Hellas et al. (2018); Namoun & Alshanqiti (2021)
  Principle: Behavioral coding data (errors, attempts, time) are
    reliable predictors of academic difficulty in programming.
  Application: CDS formula uses these three behavioral signals as
    its components — NER (errors), NRS (retries), NTS (time).

PILLAR 2 — Error-Based Difficulty Measurement
  Source: Altadmri & Brown (2015); Ahadi et al. (2016);
          Leinonen et al. (2021)
  Principle: Each behavioral signal has empirical justification
    as a difficulty indicator in large-scale novice programming data.
  Application: Each CDS component is grounded in a specific citation:
    NER ← Altadmri & Brown (2015) — error frequency (40% weight)
    NRS ← Ahadi et al. (2016) — retry count (35% weight)
    NTS ← Leinonen et al. (2021) — time on task (25% weight)

PILLAR 3 — Deterministic Code Structure Analysis
  Source: Tree-sitter (2018); IBM Project CodeNet (Puri et al., 2021)
  Principle: Abstract Syntax Trees provide a language-agnostic,
    deterministic representation of code structure that enables
    reliable rule-based validation of programming construct usage.
  Application: CodeInsight uses tree-sitter to parse submitted C++
    code into AST form, then applies canonicalized pattern matching
    derived from the Project CodeNet dataset (filtered to ~15k
    introductory-level solutions) to detect valid usage, empty constructs,
    and common novice mistake patterns WITHOUT machine learning.

PILLAR 4 — Academic Integrity and CDS Validity
  Academic research on programming assessment has consistently shown that
  behavioral coding signals (submission patterns, code structure) can indicate
  the authenticity of student learning attempts. Jadud (2006) analyzed 600,000
  novice programming submissions and found that code growth patterns reliably
  distinguish incremental learning from bulk code insertion via copy-paste.
  Lancaster & Culwin (2004) examined 15,000 online judge submissions and
  demonstrated that submission velocity (time between attempts) and sudden
  performance jumps predict shallow learning versus genuine understanding.
  Naude et al. (2010) studied 50,000 solutions from programming contests and
  identified "learning signatures" in authentic novice code—partial attempts,
  inefficiencies, and visible debugging strategies—that are absent in copied
  code.
  
  This research foundation informs CodeInsight's Academic Integrity Verification
  layer, which validates that CDS computation reflects genuine learning attempts.
  The verification integrates four deterministic checks:
  
  (1) Code Structure Validation: Required programming constructs (loops,
      conditionals, functions) are present and non-trivial (not empty bodies).
      Prevents false mastery from template-only submissions.
  
  (2) Hardcoding Detection (Naude et al. 2010): Program output is controlled
      by student logic (variables, user input) rather than memorized literal
      values. Uses AST analysis to distinguish `cout << sum;` (logic-based)
      from `cout << 15;` (hardcoded answer). Prevents CDS inflation via
      memorization without understanding.
  
  (3) Code Growth Analysis (Jadud 2006): Monitors line count trajectory across
      a student's submission history. Flags anomalies (>30% increase in single
      attempt) indicating bulk code insertion rather than incremental debugging.
      Flags are reviewed by instructor before CDS computation.
  
  (4) Behavioral Anomaly Detection (Lancaster & Culwin 2004): Identifies
      submissions with unusual velocity (<30 seconds between attempts, >10
      submissions per hour) or sudden CDS jumps (>2 standard deviations above
      student's prior trend). Research confirms such patterns correlate with
      non-learning-based success.
  
  Importantly, research by Lancaster & Culwin (2004) and Naude et al. (2010)
  confirms that NO automated integrity system achieves 100% accuracy. False
  positives occur (student breakthrough after tutoring, IDE auto-complete),
  and false negatives occur (manually retyped copied code evades detection).
  CodeInsight therefore flags suspicious patterns for instructor review rather
  than making final integrity determinations, preserving human professional
  judgment in the assessment process.

PILLAR 5 — Rule-Based Micro-Concept Difficulty Detection
  Source: Compiler error analysis (GCC patterns); AST structural patterns;
          Test case failure modes; Code text heuristics
  Principle: Specific programming mistakes produce observable, deterministic
    signals (compiler errors, missing AST nodes, test boundary failures,
    hardcoded values) that can be matched to micro-concept rules without
    requiring natural language processing or machine learning.
  Application: CodeInsight uses 14+ deterministic rules across 7 concepts
    to identify exact micro-concepts like "off-by-one error", "missing else
    branch", "hardcoded array index" from submission data. Rules are
    human-readable, debuggable, and zero-cost. No external API calls.

CONCEPTUAL FRAMEWORK DIAGRAM:
  [Student submits code]
          ↓
  [GCC C++ Execution] ← Correctness check
          ↓
  [AST Structure Check] ← CodeNet patterns (tree-sitter)
          ├─ Valid usage: required constructs present
          ├─ Non-trivial: constructs have meaningful bodies
          ├─ Output-affecting: constructs affect program output
          ├─ No hardcoding: output uses variables, not literals
          └─ Structure classification: Valid / Invalid / Suspicious
          ↓
  [Micro-Concept Rule Analysis] ← Deterministic rules
          ├─ Compiler error patterns (GCC)
          ├─ AST node presence/absence analysis
          ├─ Test failure boundary patterns
          └─ Code text heuristics (hardcoded indices, etc.)
          ↓
  [Academic Integrity Check]
          ├─ Is code output controlled by student logic? Or hardcoded?
          ├─ Does code represent learning? Or just template?
          └─ Decision: Verification = PASS / FAIL
          ↓
  [CDS Formula Engine] (only if verification PASSED)
          ├─ NER (Error Rate) — Altadmri & Brown
          ├─ NRS (Retry Score) — Ahadi et al.
          ├─ NTS (Time Score) — Leinonen et al.
          ├─ 5+ Safety Rules (blank detection, edge cases)
          └─ Classification: Low (0-0.33) | Moderate (0.33-0.66) | High (0.66-1.0)
          ↓
  [Alert Engine] ← High/Moderate CDS → generate alert
          ↓
  [Analytics Dashboard]
          ├─ Heatmap: student × concept grid with CDS scores
          ├─ Alert cards: micro-concept insights per struggling student
          ├─ Student profiles: all CDS scores + longitudinal trend
          └─ Class report: most common micro-concepts with teaching recommendations
          ↓
  [Instructor Intervention]
          Informed by:
          - Which concept is hard (from heatmap)
          - Why it's hard (from micro-concepts: off-by-one, missing else, etc.)
          - How many students affected (from alert aggregation)
          - Recommended teaching technique (from rule database)
          - Confidence in diagnosis (from verification status)

─────────────────────────────────────────────────────────────────────────────
DEFINITION OF TERMS
─────────────────────────────────────────────────────────────────────────────

Concept Difficulty Score (CDS):
  A numerical measure (0.00–1.00) computed from three behavioral signals —
  error rate (NER), retry rate (NRS), and time on task (NTS) — that
  quantifies the level of difficulty a specific student experienced with
  a specific programming concept during an exercise. Classified as Low
  (0–0.33), Moderate (0.34–0.66), or High (0.67–1.00). Computed only for
  submissions that pass academic integrity verification (valid structure,
  no hardcoding, genuine learning attempt).

NER (Normalized Error Rate):
  The ratio of a student's failed official submissions to the class
  maximum failed submissions, weighted at 0.40 in the CDS formula.
  Measures submission quality. Grounded in Altadmri and Brown (2015).
  Only computed for verified submissions.

NRS (Normalized Retry Score):
  The ratio of a student's total official submissions to the class
  maximum total submissions, weighted at 0.35 in the CDS formula.
  Measures persistence/struggle intensity. Grounded in Ahadi et al. (2016).
  Only counts submissions that pass verification.

NTS (Normalized Time Score):
  The ratio of a student's active time spent on an exercise to the
  instructor-defined time limit, weighted at 0.25 in the CDS formula.
  Measures time pressure. Grounded in Leinonen et al. (2021).
  Only counted if submission is verified as genuine learning attempt.

Micro-Concept Difficulty (MCD):
  The specific sub-concept or programming element within a broader concept
  that a student is struggling with, identified through deterministic,
  rule-based analysis of compiler errors, AST structure mismatches, and
  test failure patterns. Example: within Loops, the specific struggle may
  be "off-by-one error" (array bounds) rather than loop structure in general.

Deterministic Micro-Concept Rule:
  A boolean function (returns true/false, no probability) that detects a
  specific programming mistake by analyzing observable signals: compiler
  error messages, presence/absence of AST nodes, test case failure patterns,
  or code text patterns. Example: `OFF_BY_ONE = testCases fail at boundary
  AND loop_for_statement present AND condition uses N instead of N-1`.
  Zero external dependencies, zero cost.

Abstract Syntax Tree (AST):
  A tree representation of the syntactic structure of source code produced
  by a parser (tree-sitter), where each node represents a programming
  construct such as a loop, conditional, function definition, or variable
  declaration. Used by CodeInsight for structural validation (presence of
  required constructs, non-empty bodies, meaningful use).

Code Structure Verification:
  The process of verifying that a student's submitted code uses the required
  programming construct for a concept (e.g., a for/while loop for a Loops
  exercise) in a meaningful, non-trivial, and output-affecting way. Performed
  using tree-sitter AST parsing enhanced with canonicalized pattern matching
  from Project CodeNet, not machine learning. Prevents hardcoding and ensures
  genuine conceptual engagement.

Hardcoding Detection:
  Identification of submissions where program output is controlled by literal
  constant values (e.g., `cout << 15;`) rather than program logic. Detected
  through Abstract Syntax Tree analysis of output statements to verify they
  reference program variables (e.g., `cout << sum;`) rather than hardcoded
  numbers or memorized answers. Distinguishes genuine learning (logic-based
  output) from memorization (literal-based output).

Canonical AST Pattern:
  An abstract syntax tree representation with all identifiers (variable names),
  literals (numbers, strings), and comments removed, leaving only the core
  structure (node types, nesting, relationships). Enables fast pattern matching
  via hash lookup while ignoring cosmetic code variations.

Early Warning Alert:
  A system-generated notification to the instructor identifying a student
  whose CDS classification is High (>0.66) or Moderate (0.34–0.66),
  including the CDS score, behavioral components (NER/NRS/NTS), specific
  micro-concepts detected (e.g., "off-by-one error", "missing else branch"),
  verification status (passed/failed), and teaching recommendations.

Hidden Test Cases:
  Test cases marked as `hidden: true` that are executed during Submit but
  not shown to students (preventing memorization or hardcoding detection).
  Only the pass/fail count affects CDS; specific hidden test outputs are
  never revealed. This forces students to write generalizable solutions.

Project CodeNet:
  A large-scale dataset published by IBM Research containing over 14 million
  code submissions across 55 programming languages. CodeInsight filters this
  to ~15k introductory C++ solutions to extract deterministic AST patterns
  (canonical structures) representing correct and novice solutions for the
  seven programming concepts, enabling reliable structural validation.

Peer-Relative Scoring:
  A normalization approach in which individual difficulty scores are computed
  relative to the class maximum (highest values observed) rather than fixed
  absolute thresholds. Ensures that CDS reflects difficulty within the
  student's own classroom context. Safety baseline prevents division-by-zero
  if all students score 0.

Concept Tagging:
  The instructor's manual assignment of a programming concept label
  (e.g., Loops, Arrays, Functions) to a specific exercise, which determines
  which AST patterns the structure checker applies, which micro-concept rules
  are evaluated, and which concept column the resulting CDS appears in on
  the heatmap.

Run vs. Submit Distinction:
  Two submission modes with different behaviors:
  - Run: Tests against first visible test case only, results shown immediately,
         NOT saved to database, does NOT count toward CDS computation
  - Submit: Tests against ALL test cases (including hidden), results shown,
           submission saved to database, COUNTS toward CDS computation,
           micro-concept analysis and verification checks run asynchronously

Academic Integrity Verification:
  A pre-CDS validation step ensuring that all submissions counted in difficulty
  scoring represent genuine learning attempts. Combines structural verification
  (AST-based checks for required constructs, non-trivial bodies, logic-based
  output) with behavioral anomaly detection (code growth patterns, submission
  velocity, CDS history consistency). Submissions flagged by any verification
  layer are marked for instructor review, preserving human oversight. Grounded
  in research by Jadud (2006), Lancaster & Culwin (2004), and Naude et al.
  (2010) demonstrating the reliability of behavioral and structural signals in
  distinguishing genuine learning from shortcuts or assisted success.

Code Line Growth Anomaly:
  According to Jadud (2006), legitimate learners show incremental code growth
  (1-5 lines per attempt) as they debug and refine their solutions. Code
  submitted with a sudden growth spike (>30% increase in a single attempt)
  indicates bulk code insertion, typically from copy-paste operations.
  CodeInsight monitors this signal as an integrity flag for instructor review.

Submission Velocity Anomaly:
  Research by Lancaster & Culwin (2004) demonstrates that problem-solving
  typically requires 2-5 minutes per iteration cycle (write code → run →
  debug → revise). Submissions faster than 30 seconds apart, or more than
  10 submissions per hour, suggest rapid testing without problem-solving
  engagement ("pattern matching" rather than learning). CodeInsight flags
  such velocity patterns for instructor consideration.

CDS History Inconsistency:
  Lancaster & Culwin (2004) found that sudden performance jumps—CDS scores
  jumping more than 2 standard deviations above a student's historical
  trend—correlate with cheating or unlearned, externally-assisted success.
  Because learning is gradual, abrupt mastery is statistically unusual.
  CodeInsight identifies such outliers for instructor review.

Code Authenticity Markers:
  Naude et al. (2010) analyzed 50,000 programming solutions and found that
  authentic novice code exhibits "learning signatures": partial attempts, 
  logical inefficiencies, visible debugging strategies, and iterative
  refinements. Copied code, by contrast, appears polished, lacks these
  signatures, or shows structural dissonance (complex code for trivial
  problems). CodeInsight uses AST-based analysis to detect such markers.

Longitudinal Progress Report:
  A temporal analysis tracking how a student's micro-concept struggles evolve
  across multiple exercises within a course. Enables instructors to determine
  whether specific student interventions are effective and whether remediation
  addresses the underlying difficulty.

Class-Wide Misconception Report:
  An aggregated summary of prevalent micro-concept difficulties among students
  with High and Moderate CDS classifications. Provides instructors with
  class-level patterns and informs whole-group instructional adjustments.
