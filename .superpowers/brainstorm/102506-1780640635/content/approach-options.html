Three approaches to the mobile design surface

The structural question: how do we organize the mobile experience? All three approaches honor the 6 decisions you've already made (daily-driver students, read-only phone editor, three nav layouts by breakpoint, summary-on-phone charts, CSS-first, no new endpoints). The difference is in the IA pattern that ties them together.

A

Triage + Guide shells (role-keyed IA)

Two reusable mobile shells: MobileInstructorShell (triage cards, top-down) and MobileStudentShell (today focus + action stack, bottom-up). Every page picks the shell for its role. Simple mental model, fast to implement, but the instructor and student mental models are different — you'll see "two CodeInsights" on mobile. Defensible for defense: each role's mobile flow maps 1:1 to the thesis objective it serves.

B

Single shell, role-aware widgets (Recommended)

One MobileShell with role-aware widgets. The same shell renders for both roles — bottom nav, app bar, content area — but the content area composes from role-specific widgets (PriorityInsightCard for instructor, TodayFocusCard for student). The mobile shell is one product; the contents differ. Matches the desktop spec's "three actors, one mental model, three lenses" stance. Same code path, more shared infrastructure. (Recommended — the most consistent with the existing design system.)

C

Three separate mobile apps (instructor / student / admin)

Three completely separate mobile experiences with their own routes, their own nav, their own design language — instructor gets a triage app, student gets a learning app, admin gets an oversight app. Most clarity per audience, most code to maintain. Risks scope creep and inconsistent tokens. Not recommended for a thesis-defense v1.
