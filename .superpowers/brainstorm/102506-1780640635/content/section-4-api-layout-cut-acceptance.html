Section 4 — API contracts, layout-config schema, cut list, acceptance criteria

The "make it real" section. Section 1–3 defined what the screens look like; Section 4 defines what data they consume, what the shell's role-resolved config looks like, what we explicitly do not ship, and the metrics that decide if v1 is successful. Everything here is consistent with the prior sections and the existing 50+ endpoints.

1. The role-resolved layout config (the shell's contract)

The mobile shell does not branch on user.role inside React. Instead, a single useLayoutConfig(role, viewport) hook returns one of three config objects. The shell renders exactly what's in the config — no conditional components, no role-specific JSX. Tablet+ uses a different config object; the shell switches at the root via the mode prop and never re-queries.

4. State taxonomy (NoData / LowConfidence / Healthy) — folded in from feedback

Three explicit data-states, attached to the PriorityInsight widget (the primary). State is computed from submissions_per_student and section_age_days on the client; server data is unchanged.

StateTriggerPhone copyVisual
NoData0 submissions, or section < 24h old"No exercise activity yet. Once students submit, you'll see risk signals here."Dotted outline card · single primary CTA ("Open exercises →")
LowConfidence1–2 submissions/student, or section < 14d old"Early signal. Insights sharpen as data arrives." + progress: "n of 50 submissions to full confidence"Standard card with "Limited" badge · progress bar · secondary widgets show dotted placeholders
Healthy≥ 3 submissions/student AND section ≥ 14d oldFull insight copy (the existing PriorityInsight widget)Standard layout as designed in Section 3

Each secondary/tertiary widget also has its own state. If a single widget receives 0 rows in its data (e.g., no integrity flags), it's hidden — not rendered with empty state. That avoids the visual "lots of empty cards" anti-pattern.

5. The cut list (explicit YAGNI for v1)

Things we do not ship in v1, listed so the defense committee and the reviewer can see the boundary. Everything on this list is a v2 candidate, not a v1 omission.

  • ❌ Native mobile apps (iOS / Android). Web responsive only. (Existing spec line 645.)
  • ❌ Real-time push / websockets. Mobile reads on-demand; pull-to-refresh is the only real-time affordance. (Existing spec.)
  • ❌ Mobile flag review UI for instructors. Phone shows the count + 3 most recent; review requires tablet/desktop. Honest about cost of false positives on a 5-inch screen.
  • ❌ Mobile code editing. Phone shows the code; tablet+ opens the editor. We refuse to ship a worse-than-useless phone code experience.
  • ❌ Voice input / camera OCR for code. Not in scope.
  • ❌ Offline-first / service worker. Responsive web only — PWA was rejected in clarifying questions. Mobile requires connectivity.
  • ❌ Mobile bulk export (admin). Desktop only. Honest about the workflow cost.
  • ❌ Mobile user management (admin). Desktop only.
  • ❌ Custom widget reordering. The role-resolved config is the order. No drag-to-reorder on phone.
  • ❌ Theme toggle on phone. Auto by default; exposed via app-bar menu. (Existing spec.)
  • ❌ Mobile-only KPI definitions or scoring overrides. Mobile reads the same CDS thresholds as desktop; v1 has no "mobile mode" of CDS.
  • ❌ Instructor writing intervention notes on phone. Phone can trigger the intervention (assign Set B, message 1:1); the note-taking surface is tablet/desktop.

7. Out of scope for the mobile spec, in scope for the v1 release

  • ✅ Existing 50+ endpoints remain functional. No deprecation, no removal, no modification of response shape.
  • ✅ The desktop layout (already shipped per the existing spec at docs/superpowers/specs/2026-06-05-codeinsight-redesign-design.md) is the source of truth for visual language. Mobile is a layout transformation of the same components — not a separate design system.
  • ✅ The 12-molecule component library (CDSPill, CDSGauge, RiskBadge, InsightCard, etc.) is reused. New molecules: CodePreviewSurface (phone-only), StateAwareShell (wraps PriorityInsight for NoData / LowConfidence / Healthy), AtRiskRoster (filterable list), ActionStack, SnapshotMetrics, TopStrugglingConcepts, ConceptMasteryBarSet, WeeklyProgress, EvaluationProgress, Iso25010Instrument, IntegrityFlagList, IntegrityFlagCount, IntegrityFlagHistory, OpenFullEditorHint, DesktopOnlyNotice, ClassProfileRadar, WeeklyTeachingInsight, ExerciseCardList, TestResultList, WeakestConceptBar, StudentTodayFocus, InstructorPriorityInsight, AuditLog.
